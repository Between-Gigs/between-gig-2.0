# Legacy blank-travel compatibility — local successor, NOT ACTIVATED

This replaces the earlier global required-travel rollout proposal for location12–14. Original tested candidates remain preserved. No live profiles/settings queried, no real cutoff allocated, no flags/settings enabled, no deployment or email. Test dates are fictional fixtures only.

## Non-destructive rule

A new generic profiles setting, `submit_requirements_created_after`, maps profile-field names to canonical UTC cutoffs (`YYYY-MM-DDTHH:mm:ss.sssZ`). Default `{}` preserves previous behavior. The API reads the profile record's trusted immutable creation metadata in the same transaction. Before cutoff: existing draft/submitted/approved profiles can retain a blank answer and follow their normal save/review flow. At or after cutoff (inclusive): that field must be supplied for submission, approval and completeness-dependent re-edits. `updatedAt`, status and client JSON never select the cohort.

The new recipe removes global `travel_notes` requiredness and starts with an EMPTY cohort map. It declares that map `installOnly`, so recipe reapplication preserves an operator-owned cutoff. It neither chooses a date nor backfills any answer/date. A cohort key duplicated in global submit/approval requirements is rejected, preventing accidental global requiredness from defeating compatibility. Existing unrelated requirements, limits, authorization, catalog-service approval, media publication and privacy remain enforced.

Before-cutoff blank travel remains blank unless the person supplies an answer. Existing nonblank free text is still valid and readable; four approved choices remain available. There is no automatic default, field truncation, record/media migration, creation-date rewrite or forced taxonomy. An existing profile's cohort does not move when it is edited or reapproved.

## Client contract and authority

`ProfileDraft.profileCreatedAt` is read-only metadata outside writable `fields`. BFF GET/save derive it only from the authenticated API profile row's `createdAt`; `savedAt` still means last update. Null means no stored profile row yet. Missing/invalid historical sample metadata stays unknown, not replaced with now/updatedAt. The sample preserves its initial known creation metadata across saves and does not invent one for old drafts.

The editor derives a per-profile internal template policy using the checked public cutoff. Legacy/unknown metadata remains travel-optional; a new unsaved profile or known at/after-cutoff profile requires an answer. That internal policy is never serialized into shared templates or sent as an API exemption. Browser metadata is advisory: a forged value can only alter local UI; API enforcement always uses trusted stored metadata. Missing/corrupt trusted backend creation metadata with an active cohort fails closed and needs investigation, not fabricated timestamps. Actual hosted metadata contract must be verified before activation.

All code stays default OFF behind `NEXT_PUBLIC_PROFILE_LOCATION_CONTROLS`. Both normal deployment preflights/builds receive environment variable `PROFILE_TRAVEL_REQUIRED_AFTER` as `NEXT_PUBLIC_PROFILE_TRAVEL_REQUIRED_AFTER`. When location controls are enabled, preflight now requires an actual feature-containing API minimum/source, a compatible profiles-module declaration (local proposal1.6.0, UNRESERVED), correct environment's private settings receipt and exact matching cutoff. The earlier metadata-only baseline/API1.15 is insufficient for this successor's cohort rule. `company-os.json.profileFeatures.locationControls.travelRequiredAfter` holds separate TEST and PRODUCTION slots, both NULL; release/source fields remain unallocated. Test's cutoff must not be moved or reused to make production work.

## Rollback and limits

Retain the feature API and stable cohort map while required behavior is active. Hiding the UI does not disable API requirements for newer profiles, so first verify old-client free-text input and explicit-answer recovery in test. An older API that ignores cohort settings silently drops the new requirement; no downgrade is safe solely because module sync skips a newer installed version. A separately reviewed abort can remove only the new cohort key while retaining all unrelated requirements and guards. It relaxes a business requirement and must be intentional; it does not delete or change profile values.

Never reintroduce global required travel as a rollback: that is precisely what blocks old blank profiles. Do not move the cutoff to absorb affected profiles automatically. Keep `CUSTOM_SERVICE_REVIEW_ENABLED=1` and supporting API approval guard while applicable custom requests exist; retain optional-position metadata/compatible Department UI. Existing review can unpublish an edited profile and approval publishes an eligible profile; this behavior is unchanged, not a new visibility permission model. Visible-service enforcement remains an approval-transition guard.

No immutable-revision, cross-device conflict, actual Clerk, native-video or hosted storage/CDN acceptance is added by this policy. Original-worker potentially unpushed work remains unrecovered. All originals and prior private bundles remain available.
