# Owner transactional resends

This additive change depends on the separately reviewed Company OS manual notification API. `company-os.json` requires planned Company OS 1.20.0; the release coordinator must verify the actual release includes backend PR 99 before release. No tag is reserved or created here. It does not activate a tenant, approve stored copy, publish a template, or verify email delivery. The sample email preview, stored content release, automatic trigger wiring and actual delivery receipt are separate facts.

The hub defaults to **Test email**. Profile submission, requested changes and profile publication notifications have an additional account-bound resend path. The owner enters one actual account address; Company OS resolves the person, current profile/review cycle and original notification, renders the stored published copy, and returns an immutable confirmation binding. The UI shows that copy before a separate REAL resend confirmation. Arbitrary private-message recipients and browser-provided content are refused. Invitations retain their existing deliberate recipient workflow. Sign-in codes use the genuine Clerk sign-in flow at `/login/`; retired templates have no real-send adapter.

A source file or an active automation does not establish approval. Stored content uses explicit draft, approval and publication decisions with backend audit. Source edits invalidate the matching release. These controls do not alter existing automatic dispatch. Before activation, an authorized operator must review the backend customer runbook, deploy the schema/API, verify actual tenant data and event provenance, configure eligible automations and approve/publish the exact stored content through application controls. The feature defaults off; missing backend support and unavailable or ambiguous history stay unavailable.

A confirmed request ID and binding survive same-tab navigation and reload. Uncertain outcomes retain that ID for receipt lookup/retry; the UI does not silently issue a new intent. Company OS reserves requests durably beyond its 24-hour HTTP replay window and reports missing receipt history explicitly. Queued, provider accepted and delivered are separate states. A separate intentional resend requires another confirmation; backend checks must also prevent concurrent pending deliveries from other tabs or operators.

Validation uses fictional identities, intercepted HTTP requests and a fake backend provider. No actual send or stored-template publication is part of this work. The browser fixture covers desktop/mobile and light/dark, confirmation/cancel, repeated clicks, mode/navigation/reload, owner changes, stale releases and uncertain receipts. Run `node scripts/qa/manual-email-resends.mjs`; screenshots are in `deliverables/manual-email-resends`. The invitation-preview workflow includes this fixture. The private-parser compatibility test requires `COMPANY_OS_CONTRACT_ROOT` pointing at a reviewed private Company OS checkout; see `tests/contracts/company-os/README.md`. No private backend source is copied into this repository.
