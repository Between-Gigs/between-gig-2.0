What's built and what's left

Built (front end)

  • Public funnel: /professionals, call-sheet sign-up, /storyboard and its forms, policies
  • Invite → join → sign in (Clerk) → 5-step profile builder with autosave → submit
  • My profile, public profile /p/[slug]
  • Owners: dashboard, review queue, approve / suggest edits / undo, people search, waitlist bulk invite
  • 7 email templates as pure functions, with plain-text twins
  • QA: pnpm check (types, lint, build, screenshots, axe, end-to-end flow)

To build (backend)

  • A Worker API (one route per DataSource method, listed below)
  • D1 tables: people, invites, profile_drafts, profiles, review_notes, activity
  • Clerk token verification and the owner role check on every request
  • Email sending through the existing welcome_email_outbox and its drain (lib/welcome-email.ts)
  • Photo upload to storage (R2), URL saved in the profile
  • lib/data/api.ts: the live DataSource, exported from lib/data/index.ts

The one swap. No component imports the sample store. Write lib/data/api.ts implementing DataSource with fetch calls, then change the export in lib/data/index.ts. Leave out the optional demo block; the UI hides demo controls when it's missing.

From the call sheet to a live profile, with the endpoint and email at each step.

    W->>A: PUT /api/profile/draft

  end
  G->>W: Submit
  W->>A: POST /api/profile/submit
  A->>D: validate, copy to profiles, status submitted

"Suggest edits" instead of Approve: POST /api/owners/people/:id/request-changes writes review_notes, sets changes_requested and queues the changes-requested email; the Gigster edits and submits again.

Profile status

The value of people.status. Every transition below is the only allowed path; reject anything else with 409.

stateDiagram-v2
  direction LR
  [*] --> invited: owner invites a lead
  invited --> registered: Clerk sign-up + session/sync
  registered --> draft: first saveDraft
  draft --> submitted: submit (server-side validation)
  submitted --> approved: owner approves
  submitted --> changes_requested: owner suggests edits
  changes_requested --> submitted: Gigster resubmits
  approved --> submitted: Gigster edits and resubmits
  approved --> submitted: undo (short window)
  changes_requested --> submitted: undo (short window)

The public page reads only profiles, and only while the status is approved. Open question 3 below covers whether an approved page should stay live during a resubmission.

Emails

The Worker queues a row; the live app's drain (drainWelcomeEmails in imagine-os/between-gigs lib/welcome-email.ts, which posts to the email bridge with BG_EMAIL_BRIDGE_TOKEN) sends it. Extend it to render every template with renderEmail(template, props, { assetBase: SITE_URL, siteUrl: SITE_URL }) and sends subject, html and text from Between Gigs <hello@between-gigs.com>. Logos and artwork load from ${SITE_URL}/email/, so deploy public/email/ there.

Auth and secrets

How a request is trusted

  • The browser gets a Clerk session token (getToken()) and sends Authorization: Bearer ….
  • The Worker verifies it with @clerk/backend verifyToken, then maps sub → people.auth_user_id.
  • Owner = Clerk publicMetadata.role === "owner" (only settable from the dashboard or server).
  • Never trust an email, role or person id from a request body.
  • Joining stays invite-only: Clerk allowlist from the invite step, or reject in session/sync.

Suggested build order

Each step is shippable on its own; the front end keeps working on sample data for anything not yet live.

  1. Schema. Add the six tables with a D1 migration next to the existing ones. Index people(status, submitted_at), people(slug), people(email), invites(token_hash).
  2. Auth. A small middleware that verifies the Clerk token and loads the person and role; GET /api/session and POST /api/session/sync.
  3. Invites. GET /api/invites/:token and the owner invite batch (store a hash of a random 32-byte token).
  4. Profiles. Draft upsert, submit with server-side validation, photo upload.
  5. Owners. Review queue, approve, request changes, undo, people search, waitlist, dashboard counts and funnel.
  6. Emails. Queue rows in welcome_email_outbox with the props above; teach the existing drain to render every template with emails/*.ts.
  7. Swap. Write lib/data/api.ts, point lib/data/index.ts at it behind NEXT_PUBLIC_API_URL, and keep the sample for local QA.

Definition of done

  • The live preview runs the full journey above against the Worker: invite → join → build → submit → approve → /p/slug, with real emails arriving.
  • Every owner route returns 403 for a signed-in Gigster, and 401 without a token.
  • Status changes outside the diagram return 409.
  • pnpm check still passes locally on the sample store (it's the regression suite for the UI).
  • No secret appears in the front-end bundle (search the built out/ for sk_ and the bridge token).

Open questions for Anu

  1. Hosting. Keep the front end on Pages and call a separate Worker, or move both onto one Cloudflare project (then @clerk/nextjs with middleware becomes possible)?
  2. Profile storage. New profile_drafts / profiles tables, or rows in the existing form_responses? The interface works with either.
  3. Approved Gigsters who edit. Should the old approved version stay public while the new one waits for review? (Today a resubmission takes the page down.)
  4. Invite waves. One batch for all ≈500, or waves by ZIP or interest? The waitlist filters support waves.
  5. Reminders. A reminder for invites not opened after N days, and who sends it?
  6. Photos. R2 bucket and size limits; resize on upload or on read?
